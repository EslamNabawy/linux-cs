# Content Library Overhaul — Implementation Plan

> **For Hermes:** Execute phase-by-phase in order. Run `npm run build:data` after every data change and `npm run build` before declaring done. Commit after each phase.

**Goal:** Turn the "Linux 101 Content" section from a confusing flat wall of 13 cards (with 6 hidden/broken guides and dead icons) into a clear, guided learning hub: grouped tracks, honest metadata, working search integration, and prev/next reading flow.

**Architecture:** Single source of truth for guide metadata moves to `scripts/build-content.mjs` (it already owns the markdown parsing). Generated metadata flows into `assets/js/data-lite.js` via `scripts/gen-lite.mjs`, killing the hand-maintained duplicate in `data.js` that caused the drift. UI changes stay inside the existing vanilla-JS render functions in `assets/js/app.js` plus CSS additions.

**Tech Stack:** Vanilla JS (no framework), Vite static build, Node build scripts (`npm run build:data` = build-data + gen-lite + build-content).

## Risks & tradeoffs

- **`data.js` fallback staleness** — acceptable: runtime always uses gen-lite output in the deployed bundle; the fallback only matters for exotic file:// cases, and build-content still regenerates its own JSON+JS pair.
- **Search payload size** — indexing full guide text client-side would bloat memory (~380 KB JSON already lazy-loaded). Mitigation: index part titles + first ~400 chars per part, load lazily only when spotlight opens.
- **localStorage growth** — `readGuides` is ≤19 boolean keys; negligible.
- **No test infra** — repo is a static site with zero test framework; verification is scripted consistency checks + manual smoke (adding Jest here = YAGNI).
- **Hash-route stability** — kept `content`/`library`/section ids unchanged; only labels change.
